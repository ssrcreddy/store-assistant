1. The request flow

You type in the browser
  │
  ▼  HTTPS
CloudFront (d21rzl2kfjct47.cloudfront.net)
  │  /            → S3: the React app (HTML/JS/CSS), cached at the edge
  │  /api/chat    → load balancer (adds the secret X-Origin-Verify header)
  ▼
Load balancer → ECS task → orchestrator (Spring Boot, port 8080)
  │
  ├─ 1. PII redactor     emails, phones, cards, SSN, PAN → <EMAIL_1> etc.; real values go to the vault
  ├─ 2. Response cache   same user + same (redacted) question within 60 s?  → answer immediately
  ├─ 3. Intent router    picks TEMPLATE / FAST (Haiku) / SMART (Sonnet)
  │
  ├─ TEMPLATE:  calls the mock Order API → fills a fixed sentence → done (no LLM)
  │
  └─ FAST / SMART:
       4. Prefetch       predictable lookups first (order, payment, stock, policy)
       5. LLM gateway    budget check → Claude on Bedrock (streaming)
       6. Agent loop     Claude may call more tools (up to 3 rounds), all through the tool adapter
       7. Policy engine  cancellation = proposal only → Confirm button → idempotent cancel
       8. Output guard   masks any PII Claude produced, restores placeholders for the owner only
  │
  ▼  Server-Sent Events back to the browser
status → delta (text as it's written) → action (confirm card) → answer (final text + meta)

2. Where the data comes from

DataSourceNotes
Orders, payments, stockMock APIs (mock-apis/data.js), running in the same ECS task on localhost:4000Fixed demo data held in memory. A restart resets it, for example cancelled orders come back. In a real company, these would be your existing Order, Inventory and Payment APIs.
UsersX-User-Id header from the user dropdown (u-1001 Asha, u-1002 Daniel)A demo stand-in; Cognito is the planned replacement. The mock APIs enforce ownership, so Daniel can't see Asha's orders.
Policies and help articlesorchestrator/src/main/resources/knowledge/*.md (6 documents, 30 sections)On AWS: in-memory keyword search. Locally with RAG_ENABLED=true: hybrid search in Postgres + pgvector with a local embedding model. Results carry source IDs such as returns#return-window.
Answer wordingTEMPLATE: fixed sentences in code. FAST and SMART: written by Claude from the tool results.Claude never sees the database directly, only the trimmed tool results.
CacheIn memory in the orchestrator, 60 seconds, keyed by user + redacted questionOnly Claude answers are cached. Template answers and actions (cancel, payment link) are never cached.
MetricsIn memory in the orchestrator, at /api/metricsReset when the task restarts.

Was the answer above from the cache? No. The meta field tells you which path answered every time:

  • "route":"TEMPLATE": the mock Order API plus a template, no LLM (model: none, costUsd: 0).
  • "route":"CACHE": replayed from the 60-second cache.
  • "route":"FAST" or "SMART": Claude Haiku or Sonnet wrote it. tools and prefetched show which APIs were called.

4. Seeing what happens behind the scenes

  • Logs (startup, warm-up, errors and the audit log for confirmations): 
    aws logs tail /ecs/store-assistant --follow --region us-east-1
  • Metrics: open https://d21rzl2kfjct47.cloudfront.net/api/metrics for request counts by route, cache hits, spend, p50 and p95 latency, and PII counts.
  • Exactly what was sent to Claude: only locally, at http://localhost:8080/api/debug/llm-inputs. It's turned off on AWS on purpose.

5. Remaining steps

  1. Bedrock access. Wait for AWS to finish activating it, then re-check. When a model answers, restart the task, and tests 5–12 will work on AWS.
  2. Then run the evals against AWS: 
    node evals/run-evals.mjs --base https://d21rzl2kfjct47.cloudfront.net
    The PII leak check will report that it can't read the debug endpoint, which is expected on AWS.
  3. Optional hardening: Cognito login, a WAF rate limit, and narrowing the IAM permission to the two model IDs. These are listed in infra/aws/README.md.
